# 개발자 세션 하네스 (HarnessDulgi)

> Claude Harness AI Agent, which manages and inspects Unity projects and executes builds through a build machine.

게임 클라이언트 프로젝트에서 AI 코딩 에이전트를 **한 명의 팀원처럼** 운영하기 위해 만든 구조입니다.
컨텍스트 압축이나 세션 재시작을 거쳐도 같은 규칙과 같은 맥락으로 일하게 만드는 것이 목표입니다.

실제 상용 프로젝트에서 수개월간 운영한 구조를, 사내 정보를 제거하고 일반화해 정리했습니다.

---

## 왜 만들었나

AI 코딩 도구를 쓰다 보면 세 가지 지점에서 막힙니다.

1. **대화가 길어지면 맥락이 날아갑니다.** 컨텍스트가 압축되는 순간 앞에서 합의한 규칙, 진행 중이던 작업, 사람과 한 약속이 사라집니다. 매번 다시 설명하게 됩니다.
2. **에이전트가 건드리면 안 되는 것을 건드립니다.** 운영 DB, 배포, 메인 브랜치. 프롬프트로 "하지 마"라고 적어 두는 것만으로는 부족합니다.
3. **같은 실수가 반복됩니다.** 지난주에 겪은 함정을 이번 주에 또 밟습니다.

이 하네스는 각각에 대응합니다. 기억을 파일로 남기고, 권한을 구조적으로 막고, 교훈을 축적합니다.

---

## 전체 구조

| 층 | 구성 | 역할 |
|---|---|---|
| 규칙 | 런타임 규칙 → `CLAUDE.md` → 역할별 온보딩 → 도메인 문서 | 무엇을 해도 되고 안 되는지 |
| 기억 | `MEMORY.md`(색인) → `memory/*.md`(사실) → 작업 일지 | 압축을 넘어 유지되는 맥락 |
| 자동화 | 컴팩트 전후 훅 · 상태줄 · 스케줄 태스크 | 사람이 개입하지 않아도 도는 부분 |
| 도구 | 에디터 MCP · 이슈 트래커 · 채팅 수신 | 에이전트가 실제로 만지는 것 |
| 산출 | 브랜치 · 커밋 메시지 · 이슈 코멘트 · 조사 계획서 | 다음 세션이 읽을 기록 |

핵심 기록은 세 가지입니다. **작업 일지 · 이슈 코멘트 · 커밋 메시지.**
이 셋이 서로를 참조하게 만들어, 어느 하나만 열어도 맥락이 복원되도록 했습니다.

---

## 1. 권한을 구조로 막기

프롬프트에 "하지 마"라고 쓰는 것은 최후의 방어선입니다. 그 앞에 구조적 차단을 둡니다.

### 역할 분리

세션을 역할별로 나누고 권한을 다르게 줍니다.

| 역할 | 권한 |
|---|---|
| 리드 세션 | 머지, 배포, 결정 기록, 운영 환경 접근 |
| 작업 세션 | 자기 레인 브랜치 push, 조사, 수정 제안 |

작업 세션은 자기 브랜치 바깥으로 나갈 수 없습니다. 리드에게 보낼 요청은 이슈로 남깁니다.
사람이 승인 지점에 서 있게 되므로, 판단이 필요한 변경이 조용히 넘어가지 않습니다.

### 금지 목록

작업 세션 기준으로 네 가지를 막았습니다.

- 메인 브랜치 머지 및 직접 push
- 운영 DB·서버 접근
- 배포
- 상위 권한 시크릿 사용

### 구조적 차단이 프롬프트보다 나은 이유

위 네 가지를 **그냥 할 수 없게** 만들어 두면, 에이전트가 규칙을 잊어도 사고가 나지 않습니다.

- 운영 DB 키를 작업 PC에 두지 않음 → 접근하려 해도 수단이 없음
- 상위 권한 MCP 서버를 설정에서 차단 → 호출 자체가 실패
- 브랜치 보호 규칙 → push가 거부됨

규칙을 지키는지 감시하는 대신, 어길 수 없는 상태를 만드는 쪽이 비용이 훨씬 적습니다.

### 충돌 구역 미리 나누기

여러 세션이 병렬로 일하면 같은 자원을 두고 부딪힙니다. 겪어 보니 충돌은 거의 식별자에서 났습니다.

- 마이그레이션 번호: 리드는 홀수, 작업 세션은 짝수
- 그 외 전역 식별자: 예약 표를 저장소에 두고 선점

번호 규칙 하나로 마이그레이션 충돌은 사라졌습니다. 반대로 표를 만들지 않은 식별자에서는 계속 부딪혔습니다.
**병렬로 돌릴 계획이라면 충돌 구역을 먼저 나누는 것이 가장 싸게 먹히는 작업입니다.**

## 2. 기억 — 압축을 넘는 방법

컨텍스트 압축은 피할 수 없습니다. 압축되어도 살아남는 곳에 기록을 옮겨 두는 것이 유일한 해법입니다.

### 3층 구조

| 파일 | 내용 | 특징 |
|---|---|---|
| `memory/MEMORY.md` | 색인. 한 줄에 하나 | 매 세션 자동 로드. **크기 한도 있음** |
| `memory/*.md` | 사실 1건 = 파일 1개 | 필요할 때만 읽음 |
| `memory/session-log.md` | 작업 일지 | 최신 블록이 맨 위 |

색인만 항상 읽고, 사실 파일은 필요할 때 펼칩니다. 매 세션 전부 읽으면 토큰이 감당이 안 되기 때문입니다.

사실 파일은 frontmatter로 종류를 구분합니다.

```markdown
---
name: migration-number-parity
description: 마이그레이션 번호는 레인별로 홀짝을 나눠 쓴다
metadata:
  type: project
---

마이그레이션 파일 번호는 리드 세션이 홀수, 작업 세션이 짝수를 쓴다.

**왜:** 두 세션이 병렬로 마이그레이션을 만들면서 같은 번호를 선점해 두 번 충돌했다.
**적용:** 새 마이그레이션 파일을 만들기 전에 자기 레인의 패리티를 확인한다.
```

`type`은 네 가지입니다.

- `user` — 함께 일하는 사람에 대한 것
- `feedback` — 일하는 방식에 대해 받은 피드백. 반드시 이유를 같이 적음
- `project` — 코드나 git 기록에서 알 수 없는 프로젝트 맥락
- `reference` — 외부 자료 링크

### 한 사실은 한 곳에만

같은 내용을 여러 곳에 적으면 곧 서로 어긋납니다. 기록 위치를 미리 정해 뒀습니다.

| 무엇 | 어디 |
|---|---|
| 코드 변경의 무엇·왜 | 커밋 메시지 |
| 조사 결과 보고 | 이슈 코멘트 |
| 세션을 넘어 쓸 교훈 | `memory/` |
| 도메인 설계 | 도메인 문서 |
| 되돌릴 수 없는 결정 | 결정 기록 (리드만 작성) |
| 하루 흐름 | 작업 일지 |

### 압축 순서

1. 작업 일지 맨 위에 재개 블록 삽입 → 색인 갱신 → 백업
2. 압축 실행. PreCompact 훅이 작업 트리를 별도 브랜치에 스냅샷
3. 압축 후 SessionStart 훅이 역할 정의와 현황을 다시 주입
4. 색인 → 작업 일지 최신 블록 순으로 읽고 재개

재개 블록에는 이것만 적습니다. 많이 적으면 다음 세션이 다 읽지 않습니다.

- 지금 무엇을 하던 중이었나
- 다음 한 걸음
- 사람의 답을 기다리는 항목
- 검증하지 못한 채 넘어간 것

### 겪은 함정

- **삽입 위치를 문자열로 찾지 말 것.** 구분선(`---`)으로 위치를 잡으면 본문의 구분선에 걸려 엉뚱한 자리에 들어갑니다. 라인 번호 기준으로 삽입하고, 삽입 전에 백업을 남깁니다.
- **일지는 반드시 비대해집니다.** 한도를 정해 두고, 오래된 블록은 별도 파일로 보냅니다. 처음부터 아카이브 규칙을 만들어 두는 편이 낫습니다.
- **색인 한도를 감시할 것.** 자동 로드되는 파일이라 넘치면 세션 시작부터 손해입니다.

## 3. 자동화

모델 토큰을 쓰지 않고 셸에서 도는 것들입니다. 에이전트가 신경 쓰지 않아도 되는 일은 전부 바깥으로 뺐습니다.

| 장치 | 하는 일 |
|---|---|
| 상태줄 | 컨텍스트 사용률 표시. 임계 도달 시 신호 파일 생성 |
| PreCompact 훅 | 압축 직전 작업 트리를 스냅샷 브랜치에 저장 |
| SessionStart 훅 | 압축·재시작 후 역할 정의와 현황을 다시 주입 |
| 스케줄 태스크 | 멘션 수집 → 이슈 등록, 회신 감시, 리마인드 |
| 채팅 수신기 | 채팅 플랫폼 메시지를 로컬 파일에 적재 |

### PreCompact 훅이 하는 일

압축 과정에서 무언가 꼬이면 작업 중이던 변경을 잃을 수 있습니다. 압축 직전에 현재 작업 트리를 스냅샷 브랜치로 커밋해 둡니다. 되돌릴 일이 없으면 그대로 버려지고, 있으면 꺼내 쓸 수 있습니다.

### SessionStart 훅이 하는 일

압축 후 에이전트는 자기가 누구인지부터 흐려집니다. 역할·권한·현재 브랜치·대기 항목을 다시 주입합니다.
이 한 줄이 "작업 세션인데 머지를 시도하는" 상황을 막아 줍니다.

---

### 프롬프트 설계

에이전트별 프롬프트와, **각 제약을 왜 걸었는지**를 [`prompts/`](prompts/)에 정리해 두었습니다.
제약 대부분은 처음부터 있던 것이 아니라 한 번씩 겪고 나서 추가된 것이라, 프롬프트 본문보다 그 맥락이 더 쓸모 있다고 보고 함께 남겼습니다.

반복해서 확인한 것 네 가지입니다.

- **금지 목록보다 범위 지정이 낫다.** "하지 마"를 길게 나열해도 지켜지지 않는다. 할 수 있는 범위를 좁게 정하면 나머지는 자연히 빠진다.
- **프롬프트는 최후의 방어선이다.** 조사 에이전트에 "수정하지 마"라고 쓰는 것보다 쓰기 도구를 주지 않는 쪽이 확실하다.
- **추상적인 지시 대신 참조할 실물을 준다.** "기존 스타일을 따르라"는 거의 작동하지 않는다. "같은 폴더의 파일을 먼저 읽어라"는 작동한다.
- **확인한 것과 추정한 것을 나눠 쓰게 한다.** 틀린 것보다 틀렸는지 알 수 없다는 점이 더 비싸다.

## 4. 도구를 쓸 때의 원칙

### 에디터와 연동하기 (Unity MCP)

에디터 상태를 직접 읽게 하면 맥락 전달 비용이 크게 줄어듭니다. 프리팹과 씬의 실제 값을 재고, 컴파일 결과를 확인하고, 빌드 메뉴를 실행할 수 있습니다.

다만 **에디터는 사람의 것일 수도 있습니다.** 사람이 Play 중인 에디터를 에이전트가 건드리면 작업을 날립니다.

- Play 상태를 바꾸지 않음
- 컴파일 요청 전에 재생 중인지 확인
- 결과는 콘솔이 아니라 파일로 써서 읽음

### 컴파일 확인은 생각보다 어렵습니다

에디터를 통한 컴파일 확인은 우회적이라 실패가 조용히 지나갈 수 있습니다. 확인 방법을 여러 겹으로 겹쳐 두었습니다.

- 어셈블리 수정 시각 변화
- 컴파일된 산출물에서 심볼 검색
- 콘솔 에러 수집

그래도 잡히지 않는 것이 있습니다. 한계를 문서에 적어 두고, 여기에 걸리는 변경은 사람이 직접 확인하도록 표시합니다.
**확인 수단의 한계를 명시해 두는 것이, 확인했다고 착각하는 것보다 안전합니다.**

### 셸 이스케이프

도구를 거치면서 백슬래시가 접히거나 따옴표가 사라져 파일이 비어 버리는 사고를 겪었습니다.

- 복잡한 명령은 한 줄로 밀어 넣지 말고 **파일로 저장한 뒤 실행**
- 커밋 메시지나 JSON 페이로드는 임시 파일을 거쳐 전달
- 이스케이프 규칙을 규칙 문서에 명시

### 스키마 변경

운영 DB에는 접근하지 않습니다. 스테이징 환경도 에이전트가 직접 적용하지 않고 마이그레이션 파일만 작성합니다. 적용은 사람이 합니다.

적용 직전에 현재 상태를 조회해 충돌을 확인하는 절차를 넣었습니다. 저장소 바깥에서 선점된 식별자는 파일만 봐서는 알 수 없기 때문입니다.

## 5. 산출물 규칙

### 커밋

한 이슈에 한 커밋. 판정이 갈릴 수 있는 변경은 분리합니다.

커밋 본문에 네 가지를 적습니다.

- 무엇을 바꿨나
- 왜 바꿨나
- 어떻게 검증했나
- **검증하지 못한 것은 무엇인가**

마지막 항목이 중요합니다. 검증 공백을 숨기지 않고 기록으로 남겨야, 나중에 문제가 생겼을 때 어디부터 볼지 알 수 있습니다.

### 이슈 코멘트

조사 보고의 정본입니다. 머리에 자동 생성 표시와 날짜를 붙이고, 이전 보고를 정정할 때는 정정이라고 명시합니다.
사람이 읽는 기록이자 다음 세션이 읽는 기록이므로, 결론만 쓰지 않고 근거가 된 파일과 라인을 함께 남깁니다.

### 공유 파일 다루기

여러 사람이 동시에 수정하는 파일(씬, 설정, 에셋)은 로컬 변경이 상시 섞입니다. 전체를 커밋하면 남의 작업을 덮어씁니다.

변경 헝크 단위로 골라서 스테이징하는 스크립트를 만들어 두고, 공유 파일은 반드시 그 경로로만 커밋했습니다.

## 6. 운영하면서 알게 된 것

### 잘 작동한 것

- **압축을 여러 번 거쳐도 규칙과 미완 목록이 유지됐습니다.** 기록을 파일로 옮겨 둔 덕분입니다.
- **축적된 결함 패턴이 새 결함을 잡아냈습니다.** 과거에 겪은 유형이 메모리에 남아 있으면, 비슷한 코드를 볼 때 먼저 의심합니다.
- **주석 대신 실측했습니다.** 주석이 오래되어 틀린 경우를 몇 번 겪은 뒤로, 값은 에디터에서 직접 재고 호출 지점은 검색으로 확인하는 절차를 넣었습니다.
- **기록이 서로 참조하게 만든 것이 컸습니다.** 커밋에서 이슈로, 이슈에서 계획서로 이어지니 어디서 시작해도 맥락이 복원됩니다.
- **권한을 구조로 막아 두니 사고 가능성이 0이 됐습니다.** 규칙을 잊어도 할 수 없는 상태였기 때문입니다.

### 어려웠던 것

- **기록은 반드시 비대해집니다.** 아카이브 규칙을 처음부터 만들어 두지 않으면 나중에 손이 많이 갑니다.
- **검증 공백이 쌓입니다.** 환경 문제로 실기 검증이 막히면 컴파일 확인까지만 된 커밋이 계속 쌓입니다. 한도를 정해 두고 초과하면 경고하도록 만드는 편이 낫습니다.
- **확인 수단이 우회적이면 실패가 조용히 지나갑니다.** 확인했다는 사실보다 무엇을 확인하지 못했는지가 더 중요합니다.
- **병렬 작업의 충돌은 식별자에서 납니다.** 규칙을 만든 쪽은 해결됐고, 안 만든 쪽은 계속 부딪혔습니다.
- **주석을 믿고 검색을 건너뛰면 사고가 납니다.** 몇 번 겪은 뒤 착수 전 확인 질문을 템플릿에 넣었습니다.

### 다음에 만든다면

1. 일지 삽입을 스크립트로 고정 — 라인 기준 삽입 + 한도 확인 + 백업을 한 번에
2. 컴파일 확인을 스크립트화하고, 확인 불가 항목을 명시적으로 출력
3. 셸 이스케이프 규칙을 규칙 문서 상단에
4. 착수 전 확인 질문(호출 지점·소유자·미완 표시 여부)을 계획서 템플릿에
5. 검증 공백 한도 — N커밋 또는 D일 초과 시 경고
6. 전역 식별자 예약 표를 저장소에
7. 일지 아카이브 — 오래된 블록은 별 파일로, 본체 크기 상한 유지
8. 읽기 전용 정찰 서브에이전트 — 조사만 하고 수정은 못 하는 역할
