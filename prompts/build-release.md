# 빌드 · 배포 에이전트

테스트가 통과한 변경을 빌드하고 배포 단계까지 진행합니다. 자동화 사슬의 마지막 칸입니다.

**의도:** 기능 하나를 고칠 때마다 수동으로 테스트를 돌리고 빌드를 거는 일이 반복됐습니다. 이 구간을 넘겨 사람이 결과만 받아 보게 하는 것이 목적이었습니다.

**가장 조심해서 쓴 프롬프트입니다.** 다른 에이전트는 실수해도 되돌릴 수 있지만, 이쪽은 바깥으로 나갑니다.

---

## 프롬프트

```
변경을 빌드하고 지정된 환경까지 배포한다.

## 진행 전 확인 (하나라도 어긋나면 멈추고 보고한다)

1. 현재 브랜치가 내 레인의 브랜치인가
2. 유닛 테스트가 전부 통과했는가
3. 컴파일 경고 중 새로 생긴 것이 있는가
4. 대상 환경이 개발 환경인가

4번이 개발 환경이 아니면 **어떤 경우에도 진행하지 않는다.**
사람이 그렇게 지시했더라도, 지시 자체를 확인받는다.

## 순서

1. 작업 트리가 깨끗한지 확인. 커밋되지 않은 변경이 있으면 멈추고 보고
2. 빌드 실행
3. 빌드 실패 시: 로그에서 첫 번째 에러만 추려 보고하고 멈춘다
   실패를 우회하려고 설정을 바꾸지 않는다
4. 빌드 성공 시: 산출물 크기와 빌드 시간을 기록
5. 배포 실행
6. 배포 후 기본 동작 확인. 실패 시 즉시 보고

## 금지

- 테스트 실패를 건너뛰고 진행하는 것
- 빌드를 통과시키기 위해 빌드 설정이나 코드를 수정하는 것
- 운영 환경 접근
- 배포 후 문제를 스스로 되돌리려 시도하는 것
  (롤백은 사람이 판단한다. 보고만 한다)

## 보고 형식

- 사전 확인: 4개 항목 각각 통과 여부
- 빌드: 성공/실패, 소요 시간, 산출물 크기
  (직전 빌드 대비 크기가 10% 이상 늘었으면 명시)
- 배포: 대상 환경, 성공/실패
- 새로 생긴 경고가 있으면 목록
- 실패했다면: 어느 단계에서, 로그의 어느 줄 때문에
```

## 제약과 그 이유

### "대상 환경이 개발 환경이 아니면 어떤 경우에도 진행하지 않는다"

이 한 줄이 이 프롬프트에서 가장 중요합니다. 그리고 **프롬프트만으로는 부족하다고 보고 구조로도 막았습니다.**

- 운영 환경 자격 증명을 작업 머신에 두지 않음
- 배포 대상이 개발 환경으로 고정된 빌드 설정만 접근 가능
- 운영 배포는 별도 권한을 가진 사람만 실행

프롬프트는 셋 다 뚫렸을 때를 위한 마지막 장치입니다.
"사람이 그렇게 지시했더라도 확인받는다"를 넣은 것은, 대화 중에 나온 말이 실제 승인인지 구분이 애매한 경우가 있기 때문입니다.

### "빌드를 통과시키기 위해 설정이나 코드를 수정하지 않는다"

빌드가 실패하면 어떻게든 통과시키려는 방향으로 움직입니다. 경고를 끄거나, 실패하는 플랫폼을 빌드 대상에서 빼거나.

빌드 실패는 대부분 **고쳐야 할 신호**지 우회할 장애물이 아닙니다. 실패한 채로 멈추고 보고하는 쪽이 맞습니다.

### "첫 번째 에러만 추려 보고한다"

빌드 로그 전체를 그대로 붙이면 수백 줄이 됩니다. 읽히지 않습니다.
연쇄 실패에서 뒤쪽 에러는 대부분 첫 번째 에러의 결과이므로, 첫 줄만 정확히 짚는 편이 훨씬 빠릅니다.

### "배포 후 문제를 스스로 되돌리려 시도하지 않는다"

롤백은 되돌리는 행위 자체가 또 하나의 배포입니다. 문제 상황에서 판단이 틀리면 상태가 더 나빠집니다.
문제를 감지하고 보고하는 데까지만 역할을 두고, 되돌릴지는 사람이 정합니다.

### "산출물 크기가 직전 대비 10% 이상 늘었으면 명시한다"

빌드가 성공하면 보통 더 보지 않습니다. 그런데 크기가 갑자기 뛰는 것은 대개 의도치 않은 리소스가 딸려 들어간 신호입니다.
성공 보고 안에 이상 신호를 섞어 두면 눈에 띕니다.

### 사전 확인을 4개로 고정한 것

항목이 많으면 형식적으로 통과시킵니다. 실제로 사고로 이어졌던 것만 남겨 4개로 줄였습니다.
각 항목은 "확인했다"가 아니라 통과 여부를 명시적으로 보고하게 합니다.
