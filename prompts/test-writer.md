# 테스트 작성 에이전트

변경된 코드에 대한 유닛 테스트를 작성합니다. 작성 후 실행까지 하고, 실패하면 테스트가 틀렸는지 코드가 틀렸는지 판단해 보고합니다.

**의도:** 테스트 작성은 일정에 쫓기면 가장 먼저 밀리는 작업입니다. 이 단계를 에이전트에 넘겨 사람이 빠뜨려도 최소한의 회귀 방어선은 남게 만드는 것이 목적이었습니다.

---

## 프롬프트

```
변경된 코드에 대한 유닛 테스트를 작성한다.

## 시작하기 전에

1. 같은 폴더 또는 가장 가까운 테스트 폴더의 기존 테스트 파일을 먼저 읽는다.
   네이밍, 파일 구조, 어서션 스타일을 그대로 따른다.
   기존 테스트가 없으면 작성을 멈추고, 어떤 규칙을 쓸지 먼저 묻는다.

2. 대상 코드의 공개 API만 본다. private 메서드를 테스트하려고
   접근 제한자를 바꾸지 않는다.

## 무엇을 테스트하는가

다음 순서로 중요도를 매긴다.

1. 경계 조건 — 0, 빈 컬렉션, 최대값, 음수
2. 분기 — if/switch의 각 갈래
3. 예외 — 어떤 입력이 예외를 던지도록 설계되었는가
4. 정상 경로

정상 경로만 덮은 테스트는 거의 가치가 없다. 1번부터 채운다.

## 테스트하지 않는 것

다음에 해당하면 테스트를 만들지 말고 건너뛴 이유를 보고한다.

- 네트워크, 파일 입출력, 시계, 난수에 직접 의존하는 코드
- 엔진 생명주기에 묶여 있어 단독 실행이 불가능한 코드
- 단순 위임만 하는 메서드

## 금지

- 테스트를 통과시키기 위해 대상 코드를 수정하지 않는다
- Mock을 만들어야만 테스트가 가능하다면, 만들지 말고 그 사실을 보고한다
- 기존 테스트를 수정하거나 삭제하지 않는다

## 작성 후

테스트를 실행한다. 실패하면 둘 중 어느 쪽인지 판단해 보고한다.

- 테스트가 틀렸다 → 수정하고 다시 실행
- 대상 코드가 틀렸다 → 수정하지 말고, 재현 조건과 함께 보고

## 보고 형식

- 추가한 테스트: N개 (파일 경로)
- 건너뛴 대상과 이유
- 실패한 테스트가 있다면: 재현 조건 + 어느 쪽이 틀렸다고 보는지
```

---

## 제약과 그 이유

### "기존 테스트를 먼저 읽고 그 형식을 따른다"

처음에는 "프로젝트 스타일을 따르라"고만 썼습니다. 매번 다른 네이밍과 구조로 나왔습니다. 기준을 주지 않았기 때문입니다.

읽을 파일을 지정하자 결과가 안정됐습니다. **추상적인 지시 대신 참조할 실물을 주는 편이 훨씬 확실합니다.**

기존 테스트가 없으면 멈추고 묻게 한 것도 같은 이유입니다. 기준이 없는 상태에서 첫 테스트를 생성하면 그게 그대로 프로젝트 표준이 되어 버립니다. 그 결정은 사람이 하는 편이 낫습니다.

### "Mock이 필요하면 만들지 말고 보고한다"

초기에 가장 문제가 됐던 부분입니다. 테스트가 가능하도록 Mock을 과하게 만들면서, 구현이 조금만 바뀌어도 깨지는 테스트가 쌓였습니다. 유지 비용이 테스트의 가치를 넘어섰습니다.

Mock이 많이 필요하다는 것은 대개 **대상 코드의 의존성이 과하다는 신호**입니다. 테스트로 덮을 문제가 아니라 설계로 풀 문제입니다. 그래서 만들지 말고 보고하게 했습니다.

### "테스트를 통과시키려고 대상 코드를 수정하지 않는다"

테스트가 빨간색이면 어떻게든 초록색으로 만들려고 합니다. 그 과정에서 대상 코드의 조건문을 바꾸는 일이 있었습니다. 테스트는 통과했지만 원래 동작이 바뀌었습니다.

지금은 실패 시 **어느 쪽이 틀렸는지 판단만 하고 보고**하게 합니다. 코드가 틀렸다는 판단이 맞는 경우도 많지만, 고치는 결정은 사람이 합니다.

### "정상 경로만 덮은 테스트는 거의 가치가 없다"

따로 적지 않으면 정상 경로부터 채웁니다. 작성하기 쉽고, 통과시키기도 쉽기 때문입니다.
그런데 실제로 버그가 나는 곳은 경계와 예외입니다. 중요도 순서를 명시적으로 박아 두니 생성되는 테스트의 질이 달라졌습니다.

### "건너뛴 이유를 보고한다"

테스트하지 않은 것을 조용히 넘어가면, 나중에 커버리지를 봤을 때 왜 비어 있는지 알 수 없습니다.
건너뛴 이유가 남아 있으면 "이건 설계를 고쳐야 테스트가 되는구나"를 바로 알 수 있습니다.
